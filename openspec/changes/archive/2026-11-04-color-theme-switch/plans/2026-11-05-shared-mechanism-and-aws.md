## 1.1 `cms/server/static/theme.js` and its tests
- Behavior (see design decisions 1-3): `localStorage["cms.theme"]` holds `light`, `dark` or `system`. Early apply (runs as soon as the script loads in `<head>`, before the body renders): if the saved value is `light` or `dark`, set `document.documentElement.dataset.theme` to it; otherwise leave the attribute unset (the CSS media query decides). Every `localStorage` access in `try/catch`. Switch wiring: on `DOMContentLoaded`, find `select#theme`, set its value to the saved choice (default `system`), and on `change` save the value (`system` removes the key or stores `system`) and re-apply immediately (remove the attribute for `system`). No dependency on jQuery.
- Plain script, no module syntax, usable with `<script src=...>` in `<head>` (so it must not wait for DOM to do the early apply). Keep it small (it is copied to the ranking later); a header comment says that `cmsranking/static/theme.js` must be an identical copy.
- Tests: `cmstestsuite/unit_tests/server/static_theme_js_test.py` (new). Run theme.js under `node` with a stub `document` / `window` / `localStorage` (a tiny harness script written as a Python string or a file under the test dir). Scenarios: saved dark with light system sets the attribute (before DOMContentLoaded fires); no saved choice leaves it unset; saved `system` leaves it unset; `localStorage` throwing on read and on write does not throw; choosing Dark / Light / System through the select updates the attribute and storage; the select shows the saved choice. Skip when node is absent.
- Also test (Python, no node): the file exists at `cms/server/static/theme.js` and is reachable the way the AWS templates will reference it (check how `static_url("static", ...)` resolves for AWS: `cms/server/admin/server.py` static locations; if `cms/server/static` is not searched for AWS, say so and use the existing mechanism that serves `favicon.ico`/`loading.gif`/`jq/` from there).

## 1.2 AWS
- `cms/server/admin/templates/base.html`: load `theme.js` in `<head>` before the stylesheets (synchronous, no defer); add the switch `<select id="theme">` with options `system`/`light`/`dark` labelled «Sistema», «Claro», «Oscuro» in `#sidebar_header` next to `.login_notice` (and also on the logged-out variant of the sidebar, so the login page has it: look at the `admin is undefined` branch). Give it a `title`/`aria-label`.
- `aws_style.css` (and the `<style>` blocks of `export.html`, `contest_users_import.html`, the inline colors listed in the design: `users_bulk_remove.html`, `task.html:447`, the archive banner `base.html`, `macro/activity.html:29`): move the colors to CSS custom properties. Pattern (design decision 1): the light set on `:root`; the dark set twice, inside `@media (prefers-color-scheme: dark)` under `:root:not([data-theme="light"])` and under `:root[data-theme="dark"]`; `color-scheme: light dark` on `:root` plus `color-scheme: light`/`dark` on the explicit attribute values. Group the tokens at the top of the file with a comment. Replace literal colors by `var(--…)` (about 71 occurrences, plus the 13 hex in the page `<style>` blocks). Inline `style="color: red"` etc. become classes (or `style="color: var(--…)"`).
- `prism.css`: add the dark set (use the same two selectors; Prism's classes `.token.*`), keep light as is.
- The AWS charts: the jqPlot containers on `resources.html` (and `jquery.jqplot.min.css` colors) keep a light panel in dark theme (design decision 6): wrap them in a container with an explicit light background and dark text tokens fixed to the light values.
- Tests (`cmstestsuite/unit_tests/server/admin/`): a render test of `base.html` (reuse the existing way tests render AWS templates, e.g. `taskpage_warning_test.py` / `rankinggroup_test.py` `core` block rendering; the base template may need the usual params) asserting: `theme.js` is referenced inside `<head>` before the first stylesheet; the `select#theme` has the three options with the three labels and is present both logged in and logged out; Scenario names in comments. A CSS test: the dark set is declared under both selectors with identical declarations (parse the token blocks), `color-scheme` is declared, and no literal color remains outside the token blocks in `aws_style.css` except in an allow-list (comments in the test explain each exception, e.g. `transparent`, `inherit`).
- Existing tests that count `data-utc-time` or read AWS templates must stay green: run `utc_time_inputs_test.py`, `rankinggroup_test.py`, `taskpage_warning_test.py`, `contest_test.py`, `server_test.py`, `pool_exhaustion_test.py`, `contestactivity_test.py`.

## 1.3 Contrast test (AWS part)
- New module `cmstestsuite/unit_tests/server/theme_contrast_test.py` (it will grow with CWS and RWS in later groups): a small helper that parses `--token: #hex` declarations from a stylesheet's light set (`:root {`) and dark set (the `:root[data-theme="dark"] {` block), computes WCAG relative luminance and contrast, and a declared list of (foreground token, background token, what it is) pairs for AWS: body text on page, headings, links, sidebar text, table text on row stripes, the notification and archive banners, form fields, code (Prism) text, status colors. Assert >= 4.5 for each pair in both sets. Fix tokens (not the test) when a pair fails, within reason: pick the nearest passing color and say so in the commit message. Also assert every token defined in the light set exists in the dark set (and vice versa).
